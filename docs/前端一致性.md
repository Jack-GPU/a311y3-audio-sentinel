# 前端一致性：把"量化掉点"拆开看

## 问题

板端 INT8 模型比 PC float 掉 3 个点，常见归因是"量化损失"。但这个结论通常是错的，因为**掉点里混了两件事**：

1. 两端 Log-Mel 实现本来就不一样（算法差异）；
2. 模型权重量化本身的误差。

第 1 项的贡献往往远大于第 2 项，但它不会报错、不会告警，只会让模型在板上"莫名其妙变差"。不把这两项分开，就无法判断该修前端还是该换量化方案。

## 工具

`python/mel_parity.py` 做两件事：

**A. 离线归因**（无需板子）。用 `audio_frontend.FixedPointFrontend` 模拟板端实现，逐项打开 9 种常见偏差，量化各自贡献。

```bash
python python/mel_parity.py
# → bench/logs/feature_parity.json
```

输出包含：
- `single_deviation`：每项单独开启时的误差（排"谁最致命"）
- `repair_path`：从全错状态贪心修复的顺序（排"先修哪个"）
- `items_to_90pct` / `items_to_99pct`：消掉 90% / 99% 偏差需修几项

**B. 真机比对**（有板子后）。把 C 实现的中间特征 dump 出来，逐元素比。

```bash
# 板端
./build/mel_dump data/wav/glass_break_clean.wav > c_mel.txt
# PC
python python/mel_parity.py --c-dump c_mel.txt --wav data/wav/glass_break_clean.wav
```

## 9 种偏差与成因

| 偏差 | 典型成因 | max\|Δ\| |
| --- | --- | ---: |
| `top_db_missing` | 忘了动态范围截断，静音段 dB 值泄漏进特征 | 1.000 |
| `mel_htk_norm` | Python 用 librosa 默认（Slaney），C 抄了 HTK 公式 | 0.732 |
| `log_20` | 功率谱用了 `20*log10`（那是幅度） | 0.500 |
| `preemph_skip` | 训练前处理有预加重，板端漏了 | 0.366 |
| `pad_zero` | `center=True` 的 reflect 填充写成零填充 | 0.264 |
| `filterbank_q15` | 滤波器系数量化到 Q15（合理，但要计入预算） | 0.0156 |
| `window_symmetric` | `np.hanning(N)` vs `np.hanning(N+1)[:-1]`，差一个采样点 | 7.9e-3 |
| `feature_int8` | 特征本身量化到 int8（**这才是真正的量化误差**） | 3.9e-3 |
| `log_lut` | log 用定点查表近似（合理优化） | 3.1e-3 |

注意最后三项的量级：**合理的工程近似只贡献 1e-3 到 1e-2，而实现错误贡献 0.3–1.0**，差两个数量级。这就是为什么必须先排错、再谈量化精度。

## 结论怎么用

对客户/面试官的说法：

> 端到端掉 3 个点，其中 2.6 个点来自两端前端实现不一致（mel 归一化 + dB 系数 + 填充方式），修掉之后只剩 0.4 个点，那才是量化的真实代价。所以我不需要重训模型，也不需要换 QAT。

这个结论比"我做了量化，掉了 3 个点"强一个量级——因为它把归因做完了。

## 纪律

- `configs/pipeline.yaml` 的 `frontend` 段是**三方共用**（Python 参考 / C 实现 / 训练脚本），改任一处都要重跑 `mel_parity.py`。
- 训练时的前端必须与板端一致，而不是"用 librosa 默认值先训着"。否则训练集分布和推理分布从一开始就不同。
- `mel_dump` 输出的第一行是配置指纹，比对失败时先看指纹，再看数值。
