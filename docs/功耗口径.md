# 功耗口径：为什么不能写"常开 3 mW"

## 一句话

**开发板测不出成品板的功耗，别把两者混着说。**

开发板上 DDR、PMIC、HDMI 电平转换、以太网 PHY、USB 供电全都在耗电，整板 2–4 W 是常态。而"常开 3 mW"这种数字，来自成品板：PMIC 深度休眠、外设断电、只留 always-on 域和一颗 DMIC。两者差三个数量级。

面试官如果做过消费电子，听到"开发板常开 3 mW"会立刻追问"你测的是哪条供电轨"——答不上来就是硬伤。

## 本仓库承认的两种口径

### 口径 A：活跃占空比（推荐）

```
平均功耗 ≈ Σ(域功耗 × 域占空比)
域占空比来自 cpuidle 驻留 + NPU 调用计数
```

优点：不需要额外硬件、可复现、能进 CI、能对比不同门控策略。
缺点：每个域的"满载功耗"仍需手工标定一次。

```bash
python python/board_power_budget.py --mode residency --secs 60 --label baseline
python python/board_power_budget.py --mode residency --secs 60 --label gated
```

读的是：

```
/sys/devices/system/cpu/cpu*/cpuidle/state*/{name,usage,time}
```

窗口内 `time` 的增量就是该 C-state 的驻留时间。只统计非 `poll` 状态——`poll` 是"没睡"，算进去会把结果做漂亮但毫无意义。

### 口径 B：整板平均功耗

INA226 / INA219 串在 12V 输入，1 kHz 采样。

```bash
python python/board_power_budget.py --mode ina226 --device /dev/i2c-1 --addr 0x40 --secs 60
```

这条口径给出的是**整板**数字，可以写"整板平均功耗 X W → Y W"，但不能推"芯片常开功耗"。

## 报表格式

无论用哪种口径，必须能和基线对比：

| 组 | 配置 | 占空比 | 整板 W | confirm P99 | 误唤醒/h |
| --- | --- | ---: | ---: | ---: | ---: |
| A | NPU 全程常开 | 100% | 待测 | 待测 | 待测 |
| B | CPU 门控 + NPU 确认 | 待测 | 待测 | 待测 | 待测 |
| C | 三级分级唤醒 | 待测 | 待测 | 待测 | 待测 |

**A 组不是凑数**：没有"最笨方案"做参照，"优化了 3 倍"就没有分母。

## 三个容易犯的错

1. **只报峰值功耗**。常开系统看的是平均和占空比，峰值只在散热设计时有用。
2. **忽略误唤醒的能耗代价**。一次误唤醒要把 A78 和 NPU 拉起来，代价远超稳态推理。所以"误唤醒/h"必须和功耗一起报。
3. **不区分"设备在跑"和"设备在等"**。常开系统 95% 的时间在等，等的功耗才是主项。

## 怎么讲这个 trade-off

> 我把门控阈值往上提，占空比从 42% 降到 8%，平均功耗降了约 4 倍，代价是唤醒→确认 P99 从 120 ms 涨到 300 ms，误唤醒从 3 次/h 降到 0.4 次/h。这条曲线上有个拐点：再往上提，占空比降不了多少，但漏检开始出现。我选在拐点前一点。

能讲出"拐点在哪、为什么选这里"，比报一个漂亮数字有价值得多。
